## Summary

This is a thoroughly specified feature with exceptional depth across 9 user stories, 55 functional requirements, and a well-researched technical foundation. The spec author clearly understands the domain and has anticipated most failure modes. The strongest element is the safety architecture: manifest-derived tool registry, envelope-cipher secret handling, danger-tier confirmation, and the kill-switch design form a credible defence-in-depth story. The headline weakness is a handful of cross-document inconsistencies between spec FRs and the data-model/task plan, plus a few unaddressed edge cases around concurrent budget access and long-running streaming connections that could cause budget over-spend under load.

| F3 | HIGH | Hidden assumption | Budget enforcer token reservation (FR-045) uses a "conservative estimate" before inference, but the reservation mechanism is never specified — no column, no in-memory tracker, no reconciliation schema. If two concurrent conversations both reserve 100K tokens against a remaining budget of 150K, both pass the check and overspend. plan.md mentions "conservative token reservation/reconciliation" in T010 but gives no design. | Add a `reserved_tokens_in` / `reserved_tokens_out` column pair to `ai_conversations` (or an in-memory atomic counter) and specify the reservation/reconciliation lifecycle: reserve at conversation start, reconcile with actual `usage` on complete/error/cap_exhausted. Budget check should be `SUM(actual) + SUM(reserved) >= cap`. |
| F4 | HIGH | Missing edge case | No timeout or max-duration on a conversation. A streaming conversation that receives periodic "absorb" events (push trigger dedup) could theoretically extend indefinitely — each absorbed event adds context and the LLM continues generating. There is no "max conversation wall-clock time" setting. The per-incident token cap limits tokens, but a low-cap conversation could still run for hours if the provider streams very slowly or the absorb-then-continue loop cycles. | Add a `max_conversation_duration` setting (default e.g. 30 minutes) to `ai_settings`. If elapsed time since `created_at` exceeds this, abort with a new status `aborted_by_timeout`. This is independent of token cap — it's a wall-clock safety net. |
| F5 | HIGH | Hidden assumption | `ai_messages.content_text` is `TEXT NOT NULL` — but tool-call results with empty stdout produce an empty string. The spec (FR-026) says stdout is truncated to 8KB, but doesn't specify what happens when stdout is literally empty (exit code 0, no output). Empty `content_text` for `role='tool'` may confuse the LLM's next turn. | Consider allowing `content_text` to be nullable OR defining a sentinel like `(no output)` for empty tool results. Document this in the system prompt so the LLM knows how to interpret it. |
| F6 | MEDIUM | Logical consistency | Task count mismatch: tasks.md header says "**Total**: 82 tasks" but the actual task IDs run T001–T081. Counting all items (including T039a) gives 82 entries, which is correct. However, T039a breaks the sequential numbering convention and could confuse dependency graph readers. The dependency graph (line 170) references `T039a` correctly but the "Agent Summary" table (line 242) counts 52 BE tasks — manual count of [BE]-tagged items gives 52, so this is consistent. Just a minor naming convention concern. | Consider renaming T039a to T040 and renumbering subsequent tasks (T040→T041, etc.) for clean sequential IDs. Alternatively, document that letter-suffix tasks are subtasks of the parent numeric task. Low priority. |
| F7 | MEDIUM | Missing edge case | Push dedup map is in-memory only (spec A-006, FR-017). On server restart, dedup state is lost. The spec acknowledges this ("repeated source event may create a new conversation") but doesn't address the burst scenario: if the server restarts during a health-RED flapping event, the restart triggers multiple rapid push analyses (one per health-poller cycle), each creating a separate conversation until the dedup map repopulates. This could burn through the monthly budget quickly. | Add a startup "recent conversation check" in push-subscriber initialization: before creating a new push conversation, query `ai_conversations WHERE target_kind = ? AND target_id = ? AND created_at > NOW() - INTERVAL '5 minutes'`. If a recent conversation exists, restore its dedup entry. This is a startup-only cost, not a per-event DB hit. |
| F8 | MEDIUM | Security | The `GET /api/ai/conversations/:id` endpoint (contracts/api.md line 233) returns `messages[].contentText` including the system prompt (seq 0, role=system). The system prompt contains the full confidence rubric, tool metadata, and untrusted-context instructions. A `ai:viewer` role (the weakest AI role) can read the complete system prompt. While not a direct security hole, it leaks operational internals and could help craft adversarial inputs if an operator account is compromised. | Consider either: (a) omitting `role=system` messages from the API response (operator doesn't need to see the rubric), or (b) requiring `ai:admin` for system-prompt visibility. The spec says context transparency is important (FR-013), but that applies to the *context document* (role=user), not the system prompt. |
| F9 | MEDIUM | Failure modes | No fallback for `envelope-cipher` master key becoming unavailable AFTER initial provider setup. The spec covers the "save fails" case (US1 edge case) but not the "key was available at save time but becomes unavailable during inference" case. The `resolveModel()` function calls `open(providerKey.apiKeyEncrypted)` — if this throws, the entire conversation fails. The error path should be explicit. | In `incident-analyzer.ts`, wrap `resolveModel()` in a try/catch that sets conversation status to `error`, emits `ai.analysis_failed` with `{ errorClass: 'master_key_unavailable' }`, and surfaces a clear message. This is probably the intended behavior but should be explicit in the spec or llm-provider.md contract. |
| F10 | MEDIUM | Performance | Context aggregator (FR-011, T011) runs 6 concurrent DB queries per pull-trigger analysis. Under load (10 pull analyses/min rate limit + 30 push analyses/min system limit = up to 40 concurrent aggregations), this is 240 concurrent DB queries. The spec doesn't mention connection pool sizing or query optimization for the aggregation fanout. | In plan.md or T011 description, note the connection pool consideration. Suggest using `Promise.all()` for the fanout (already implied) and confirming that the pg pool default (`postgres` package) handles 40 concurrent query bursts. If the pool is small (e.g., 10), queries will queue. Consider adding a note to check/adjust pool size during implementation. |
| F11 | MEDIUM | Alternative approaches | The spec uses an in-memory dedup map for push-trigger dedup (FR-017). For a single-process architecture this works, but the map grows unboundedly during high event volume (each unique `(target_kind, target_id, event_class)` triple gets an entry). The 300-second expiry requires a cleanup mechanism, which isn't specified. | Add explicit cleanup: either a `setInterval` sweep every 60s that removes entries older than 300s, or use a TTL-aware map library. The task description for T041 should mention cleanup logic. |
| F12 | MEDIUM | Hidden assumption | `ai_conversations.hypothesis` and `confidence` columns exist in data-model.md but are never populated in the described flow. The spec says the hypothesis is extracted from the LLM response text via `extractHypothesis(text)` (llm-provider.md line 70), but the extraction logic is unspecified. Without a structured output schema, regex-based extraction of hypothesis/confidence from free-form LLM text is fragile and provider-dependent. | Consider either: (a) using the Vercel AI SDK's structured output feature (`generateObject` with a Zod schema) for the hypothesis/confidence extraction as a post-processing step, or (b) specify the regex/parsing heuristic in llm-provider.md so it's reviewable. Option (a) adds a second LLM call but is reliable; option (b) is cheaper but brittle. |

## Alternative approaches considered

1. **Structured output via `generateObject` instead of free-text + regex extraction**: The current design has the LLM output free-form text and then extracts hypothesis/confidence via unspecified heuristics. An alternative is to use Vercel AI SDK's `generateObject` with a Zod schema for the structured parts (hypothesis, confidence, evidence list), falling back to `streamText` for the narrative. This would make `extractHypothesis` and `extractConfidence` deterministic but adds complexity and a potential second LLM call. Worth the author weighing the tradeoff — see F12.

2. **Redis/shared cache for push dedup instead of in-memory map**: The spec correctly scopes dedup to single-process (A-006). If horizontal scaling is ever on the roadmap, an in-memory map becomes a correctness bug overnight. A lightweight alternative is a pg-backed dedup table with a TTL-based cleanup, which would survive restarts (addressing F7) and scale to multiple processes. The cost is one DB write per push event. The author may consider this as a v1.1 item but should be aware of the tradeoff.

3. **Conversation-level soft budget warning before hard stop**: Currently, per-incident cap hit causes an immediate halt (`cap_exhausted`). An alternative is a soft warning at 80% cap ("approaching token limit — wind down your analysis") injected into the LLM context, giving the model a chance to conclude gracefully rather than being cut off mid-sentence. This would improve operator experience at the cost of slightly higher token usage. The author may want to add this as a future enhancement.
