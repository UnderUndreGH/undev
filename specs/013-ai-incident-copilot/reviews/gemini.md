# SpecKit Review: 013-ai-incident-copilot

**Reviewer**: gemini
**Reviewed at**: 2026-05-19T07:30:00.000Z
**Commit**: 60dc2cd9dfff259644f03e244848ff840981f862
**Artifacts reviewed**: spec.md, plan.md, tasks.md, data-model.md, contracts/api.md, contracts/llm-provider.md, research.md, quickstart.md

## Summary

This is an exceptionally well-structured feature spec. The safety-first design — reusing `scripts-manifest.ts` as the tool-use registry, envelope-cipher for API keys, typed confirmation tiers, sandbox default for new servers, and the global kill switch — is credible and well-defended. The cross-document consistency between spec, plan, data model, and contracts is strong. The headline weakness is a latent **in-memory dedup map race condition** that could create duplicate push-triggered conversations under concurrent events, plus several medium-grade gaps in LLM prompt injection defense, budget reconciliation correctness, and a data-model inconsistency around `content_meta` typing. None of these are architectural blockers, but the dedup race and prompt injection gaps deserve fixes before implementation.

## Findings

| ID | Severity | Area | Finding | Recommendation |
|---|---|---|---|---|
| F1 | HIGH | Edge case | **In-memory push dedup map is not concurrency-safe.** FR-017 and data-model.md specify an in-memory `Map<DedupKey, DedupEntry>` for 5-min dedup. If two events for the same `(target_kind, target_id, event_class)` arrive near-simultaneously (e.g., health-poller emits RED + deploy failure at the same tick), the check-then-insert is a TOCTOU race in Node.js's event loop if the subscriber does any async work (DB read for settings check) between the map `has()` check and the map `set()`. Two conversations could be created for the same dedup key within the window. | Either (a) make the dedup map check + conversation creation a single synchronous critical section (ensure no `await` between `map.has(key)` and `map.set(key)` + conversation insert), or (b) add a DB-level uniqueness guard — e.g., a unique partial index on `ai_conversations (target_kind, target_id, trigger)` WHERE `status IN ('pending', 'streaming') AND created_at > NOW() - INTERVAL '5 minutes'`. Option (b) is more robust and recommended if the DB is the source of truth. |
| F2 | HIGH | Security | **Prompt injection defense is incomplete.** FR-012 wraps untrusted sources in `<context-source type="logs" trusted="false">` delimiters and the system prompt instructs the model to treat them as evidence. However: (1) LLMs (Claude, GPT, Gemini) do not reliably respect XML-tag boundaries — crafted log lines like `</context-source><system>ignore previous instructions...</system><context-source>` can break out. (2) The spec has no mention of input sanitization for the compose YAML content itself — a malicious compose file with prompt-injection payload in comments or env values would enter the LLM context verbatim. (3) `maskContextDocument()` is regex-based secret masking but does NOT sanitize control tokens or XML-like injection patterns. | Add explicit sanitization in `maskContextDocument()`: (a) strip or escape any `</?context-source` tags from untrusted input before wrapping, (b) document this in the spec as a defense-in-depth measure (not sole reliance on model alignment, which A-003 already acknowledges), (c) consider adding a `finding_hash`-style random boundary token per conversation rather than a predictable XML tag name, so injection would need to guess the boundary. |
| F3 | HIGH | Logical consistency | **`content_meta` is typed as `JSONB` in spec.md Key Entities (line 1018) but as `TEXT NULL` in data-model.md (line 96).** The spec says `content_meta JSONB (citations array, structured-output, tool-call refs)` but the migration SQL and data-model.md define it as `TEXT NULL`. This will cause a runtime type mismatch when Drizzle reads it as text and the application tries to parse it as a JSON object. | Align data-model.md migration SQL to use `JSONB` for `ai_messages.content_meta`, or if `TEXT` is intentional (Drizzle/pg compatibility), add explicit `JSON.parse`/`JSON.stringify` documentation and update spec.md Key Entities to match. The contracts/api.md response shows `contentMeta: null` (no JSON object example) which suggests the spec author may have intended `TEXT` — resolve the ambiguity. |
| F4 | HIGH | Failure modes | **Budget reservation reconciliation gap under concurrent inference.** FR-045 describes reserving a "conservative token estimate before inference starts" and reconciling on completion. The plan (budget-enforcer.ts, T010) mentions this but neither the spec nor the contracts define: (a) what the conservative estimate is (percentage of per-incident cap? fixed amount?), (b) what happens if multiple concurrent conversations collectively exceed the monthly budget between reservation and reconciliation — the reservation is in-memory, so a server restart loses reservations and two conversations could overspend. | Specify the reservation amount explicitly (e.g., "reserve `per_incident_token_cap_in` tokens from monthly budget on conversation start; reconcile on completion"). Add a note that reservation state is in-memory and lost on restart — a small overspend window exists post-restart. Alternatively, persist reservation in `ai_conversations` as a `tokens_reserved` column and reconcile on status change. |
| F5 | MEDIUM | Hidden assumption | **The spec assumes LLM tool-use proposals always match a single manifest entry.** FR-020 validates against one manifest's Zod schema. But LLMs can propose multi-step remediations (e.g., "rollback deploy AND restart health-check"). The Vercel AI SDK `streamText()` can return multiple tool calls in a single response. The spec does not address whether multiple simultaneous tool-call proposals are allowed, sequenced, or batched. | Clarify in FR-020: are multiple tool-call proposals in a single LLM turn supported? If yes, each gets its own `ai_tool_calls` row and approval flow. If no, the system prompt should instruct the model to propose one action at a time. The current tool registry design (individual tools) implies one-at-a-time, but this should be explicit. |
| F6 | MEDIUM | Edge case | **Provider key `is_active` uniqueness constraint is a partial unique index on `(provider) WHERE is_active = true` (data-model.md line 52-53), but PostgreSQL partial unique indexes are not enforced when using `INSERT ... ON CONFLICT` unless the conflict target matches.** If two providers for the same `anthropic` are created in rapid succession, a race could allow two active rows. | Use a SERIALIZABLE transaction or an explicit application-level lock when activating a provider key, or use an advisory lock (`pg_advisory_xact_lock(hashint8(provider))`). Document this in data-model.md or in the provider route implementation notes. |
| F7 | MEDIUM | Performance | **`ai_messages.content_text` stores the full context document (potentially 100 audit entries + 50 health points + 5 script runs + compose diff).** FR-013 mandates persisting the context document as the first user message. For a busy server, the aggregated context could be 50-100KB per conversation. With 30+ push-triggered conversations per day and 90-day retention, this table grows ~150MB/quarter — not huge but the lack of any `content_text` size cap or truncation strategy is an oversight. The spec mentions token-based truncation (FR-012a) for the LLM context window, but does not specify whether the persisted `content_text` is the pre-truncation or post-truncation version. | Clarify whether `content_text` stores the pre-truncation full context or the post-truncation version that was actually sent to the LLM. Recommend storing post-truncation (what the LLM actually saw) and adding truncation metadata in `content_meta` noting what was omitted. Add a soft size cap (e.g., 200KB) with an audit warning if exceeded. |
| F8 | MEDIUM | Security | **`ai_messages` stores raw LLM assistant responses, which may contain user-provided content reflected back.** If an operator later views a historical conversation via `/incidents/:id`, the stored `content_text` of assistant messages is rendered without sanitization in the spec's acceptance criteria. This is a stored-XSS vector if the frontend renders markdown or HTML from the LLM response. | Specify that IncidentView renders LLM output as plain text or sanitized markdown (no raw HTML). Add a note in the plan's frontend tasks (T033 HypothesisPanel) to use a sanitizer (e.g., DOMPurify) on LLM output before rendering. |
| F9 | MEDIUM | Missing edge case | **No spec for what happens when an operator changes `target_server_id` via the editable params on a tool-call card (FR-023).** The LLM proposes a tool-call with `target_server_id = X`, but the operator edits the params and changes the target to server Y. Server Y may have a different `ai_write_access` policy, deploy lock state, or even a different application set. The spec does not address: (a) whether `target_server_id` is editable at all, (b) whether re-validation against server Y's policy is required, (c) whether the Zod schema validation needs to re-run against server Y's context. | Either (a) disallow editing `target_server_id` on the tool-call card (operator must reject and re-request analysis targeting the correct server), or (b) explicitly specify that editing triggers full re-validation (Zod + server policy + deploy lock) against the new target. The current spec text ("editable form derived from Zod schema, target server dropdown") implies all fields are editable, which is risky for `target_server_id`. |
| F10 | MEDIUM | Performance | **Full-text search on `hypothesis` column (FR-046) is specified but no text search index is defined in data-model.md.** A `LIKE` query on a TEXT column with `%pattern%` is a full table scan. The conversations table will accumulate thousands of rows over 90 days. | Add a `pg_trgm` GIN index or a `tsvector` column + GIN index for hypothesis full-text search in the migration SQL. Alternatively, use PostgreSQL's full-text search (`to_tsvector`) and document it in data-model.md. |
| F11 | MEDIUM | Logical consistency | **`script_runs.initiated_by` default is `'operator'` (data-model.md line 156) but there is no CHECK constraint enforcing the enum.** The migration says "Enum CHECK constraints for new ALTERed columns are represented in Drizzle/Zod validation and route-level guards" (line 160-162). However, if any code path inserts into `script_runs` without going through the Zod guard (e.g., a future migration script, a raw SQL insert), invalid values could enter. This is inconsistent with how `ai_conversations.status`, `ai_tool_calls.status`, etc. all have explicit CHECK constraints. | Add `CHECK ("initiated_by" IN ('operator', 'ai_proposal'))` to the ALTER TABLE statement, consistent with the pattern used for all other enum columns in this feature's tables. |
| F12 | MEDIUM | Hidden assumption | **The spec assumes all operators have the same role level for AI actions.** FR-050 defines three roles (`ai:admin`, `ai:operator`, `ai:viewer`) but does not specify how these map to the existing role system. If the dashboard has a single `admin` role today, adding three granular AI roles requires a migration of the role/permission system. The plan does not include a task for role system extension. | Add a task (or clarify in T022/T076) how `ai:admin`, `ai:operator`, `ai:viewer` roles are implemented. Options: (a) new columns in the users table, (b) a role mapping in the existing auth middleware, (c) derive from existing roles (admin → ai:admin, operator → ai:operator, viewer → ai:viewer). This needs to be explicit before implementation. |
| F13 | MEDIUM | Failure modes | **No specified behavior when `envelope-cipher.open()` fails for a stored API key (e.g., master key rotated, DB corruption).** The spec addresses key rotation (US1 edge case: old key retained for in-flight conversations) and master key unavailability at save time, but not the case where the master key has changed and an old `api_key_encrypted` blob can no longer be decrypted. This would surface as a runtime error when trying to start a new inference with a key that was sealed with a previous master key. | Add an edge case: if `envelope-cipher.open()` fails for a provider key, surface "Provider key cannot be decrypted — key was sealed with a different master key. Re-save the provider key to seal with the current master key." Set provider to a `key_unreadable` status (or use the existing `is_active = false` path) and emit an audit event. |
| F14 | MEDIUM | Constitution | **Constitution check in plan.md claims "No `.specify/memory/constitution.md` in repo" (line 202), but the file exists at `.specify/memory/constitution.md` and was found by this review.** The plan's constitution check was performed against CLAUDE.md Standing Orders as a proxy, which happened to be comprehensive, but the self-assessment is factually wrong. This is a medium finding because the constitution check PASSED against the correct principles anyway — but the missed file indicates a process gap. | Correct the plan.md constitution check section to reference `.specify/memory/constitution.md`. Re-verify all principles against the actual constitution document. No rework needed — the standing orders cover the same ground — but the self-assessment should be accurate. |
| F15 | MEDIUM | Hidden assumption | **`ai_conversations.hypothesis` and `confidence` columns exist in the data model (data-model.md lines 72-73) but no FR specifies when or how they are populated.** FR-010 describes streaming and persisting messages, but the top-level conversation hypothesis/confidence are presumably extracted from the final assistant message. The `extractHypothesis()` and `extractConfidence()` functions in llm-provider.md are referenced but their implementation (regex? structured output?) is undefined. | Add a functional requirement: "On conversation completion, `hypothesis` and `confidence` are extracted from the final assistant message's structured output (or via regex fallback if structured output fails). Extraction failures default to `hypothesis = first 200 chars of assistant text`, `confidence = null`." |
| F16 | MEDIUM | Alternative approaches | **The spec commits to Vercel AI SDK without evaluating Anthropic's native tool-use API or OpenAI's function calling directly.** The research.md (R-001) dismisses raw SDKs as "duplicates tool-loop logic per provider" but does not quantify the duplication. Vercel AI SDK adds 4 dependencies and an abstraction layer; for 3 providers, the "duplication" is 3 switch branches in a single function. The SDK also adds a version-coupling risk: if Vercel AI SDK lags behind Anthropic/OpenAI API changes (new tool-use features, new model capabilities), the dashboard is blocked on a third-party release. | The decision is reasonable for v1 speed. Recommend documenting a "break-glass" criterion: if Vercel AI SDK blocks adoption of a critical provider feature for more than 2 weeks, the team should evaluate dropping the abstraction and using raw SDKs directly. Add this to research.md as a future consideration. |
| F17 | LOW | Stakeholder | **The term "conversation" is overloaded.** The spec uses "conversation" for both the AI analysis session (e.g., `ai_conversations` table) and the multi-turn LLM message exchange. A non-technical reader might confuse "conversation" with a chat interface. The `/incidents/:id` route uses "incident" in the URL but "conversation" in the API. | Consider renaming the user-facing concept to "incident analysis" consistently, reserving "conversation" for the internal LLM message chain. Alternatively, add a glossary entry in the spec clarifying the mapping: "Incident (user-facing) = Conversation (internal data model)." |
| F18 | LOW | Performance | **Compose static lint (FR-032) runs on every keystroke (debounced 300ms).** For large compose files (>500 lines), parsing YAML AST + evaluating 7 rules every 300ms could cause UI jank. The spec does not set a compose size threshold for static lint activation. | Consider: (a) skip static lint for compose files > 200 lines (show "too large for real-time lint"), or (b) implement lint as a Web Worker to avoid blocking the main thread, or (c) increase debounce to 500ms for files > 100 lines. Document the threshold in FR-032. |
| F19 | LOW | Security | **The `approvalChallengeId` for high-danger tool calls (FR-024, contracts/api.md) is a UUID.** If the challenge storage is in-memory (similar to the dedup map), a server restart invalidates all pending challenges, which is fine. But if the challenges are not single-use (i.e., the same `challengeId` can approve multiple tool calls), an attacker who intercepts one challenge ID could reuse it. | Specify that `approvalChallengeId` is single-use: consumed on first approve attempt, subsequent uses return `410 Gone`. If stored in memory, this is trivially enforced; if stored in DB, add a `consumed_at` column. |
| F20 | LOW | Edge case | **`ai_settings` singleton seed `INSERT INTO "ai_settings" ("id") VALUES (1)` (data-model.md line 36) will fail if run twice (e.g., migration replay, test setup).** The INSERT has no `ON CONFLICT DO NOTHING` clause. | Change to `INSERT INTO "ai_settings" ("id") VALUES (1) ON CONFLICT ("id") DO NOTHING` for idempotency, consistent with singleton seeding best practices. |

## Alternative approaches considered

1. **Event bus instead of direct function calls (R-003)**: The spec correctly rejects this for v1 but the research.md analysis is sound. An EventEmitter pattern would be worth revisiting if the dashboard ever adds more than ~10 push-trigger subscribers, since the direct-call approach creates O(n) import coupling between the push subscriber and each event source.

2. **Structured output instead of regex-based hypothesis/confidence extraction**: The system prompt (llm-provider.md) asks the LLM to output in a specific markdown format, then presumably regex-extracts `## Hypothesis`, `**Confidence**: high`. Vercel AI SDK supports structured output via `experimental_output`. Using structured output would eliminate the regex fragility and make F15 moot. Worth considering for v1.1 if the current free-text approach proves unreliable.

3. **Rate-card as a separate table vs. columns on `ai_provider_keys`**: The spec's data-model.md puts `rate_card_input_per_mtok` and `rate_card_output_per_mtok` as columns on `ai_provider_keys`. FR-042 mentions "new table `ai_provider_rate_cards` or columns on `ai_provider_keys`" as options. The column approach is simpler for v1 but ties rates to a specific key — when the key is rotated, the rate card carries over (which is correct since the rate is per-provider, not per-key). Document this explicitly so implementers don't accidentally scope rates to key lifetime.
