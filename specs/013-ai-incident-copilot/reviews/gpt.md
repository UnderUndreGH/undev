## Summary

The feature is unusually thorough on product intent, safety gates, auditability, and operator-facing workflows; the core idea of deriving LLM tools from the existing manifest is the strongest part of the design. The biggest concern is that the artifacts diverge in several foundational places: settings storage, push-trigger architecture, DB dialect/FK targets, auth/approval contract, and dependency ordering. These are not implementation polish issues — they will cause rework or security gaps if implementation starts from the current tasks as-is.

## Alternative approaches considered

- **Durable AI job queue instead of direct calls/in-memory maps**: Current plan is intentionally single-process and light, but push triggers, budget reservation, and streaming recovery would be cleaner with a DB-backed job table. This may be too much for v1, but the design should consciously accept duplicate/lost push analyses and budget races rather than discovering them later.
- **Read-only v1 before tool-use v1**: Given the security surface, an incremental launch that ships US1+US2+US8+history first, then tool-use behind a second gate, would reduce blast radius. The current tasks combine provider integration, tool dispatch, cost, and UI in one large feature.
- **Server-issued approval challenges**: Rather than trusting UI modals for medium/high approvals, the server can return an approval challenge object when a tool call is proposed; approve requires the challenge id plus typed value after server-side cooldown expiry.
